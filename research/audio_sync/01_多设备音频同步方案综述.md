# Windows 多设备音频同步方案综述

更新时间：2026-08-10

## 1. 结论摘要

多设备音频同步不是单一的“同时调用播放函数”，至少需要同时处理：

1. 起始时间偏移（sample time offset，STO）；
2. 设备采样时钟偏差（sample-rate offset，SRO）和长期漂移；
3. 网络、编码、缓冲、WASAPI、DAC、DSP、Bluetooth 的固定或随机延迟；
4. 扬声器到听音位置的声学传播延迟。

除了主动探针，最有价值的路线是：

- 共享会话时间线 + WASAPI 硬件音频时钟；
- 利用自然音频的互相关、包络、频谱特征或音频指纹做被动同步；
- 通过 coherence drift、DXCP 等方法估计 SRO；
- 用 ASRC、PLL/PI 闭环修正缓冲和采样率；
- 对高要求场景使用共用硬件时钟、ASIO 聚合驱动或 PTP/AES67/Dante/AVB。

一个关键边界是：如果某个设备的 DAC、Bluetooth 或扬声器实际延迟从未被任何传感器观察到，那么这部分延迟在数学上不可观测，仅凭网络时间戳无法推断。无探针可以实现良好的数字同步，但不能保证不同输出链路的绝对声学同步。

## 2. 论文中最重要的发现

### 2.1 采样率偏差会不断积累

设参考设备采样周期为 \(T_r\)，设备误差为 ε：

\[
T_i=T_r(1+\varepsilon)
\]

经过 \(n\) 个采样点后，累计时间误差近似为：

\[
\tau[n]=\varepsilon n
\]

在 STFT 域中，采样率偏差表现为随时间增长的线性相位漂移：

\[
Z_i[k,l]\approx Y[k,l]
e^{j2\pi k\tau[l]/N}
\]

2023 年的 WASN 研究指出，实际异构设备的 SRO 常在约 ±100 ppm 范围内；在 16 kHz 系统中，1 Hz 的采样率偏差就会明显损害分布式声源分离和波束形成性能。[Online distributed waveform-synchronization for acoustic sensor networks](https://link.springer.com/article/10.1186/s13636-023-00311-9)

在 48 kHz 下，如果两个设备相对偏差为 200 ppm，约每秒积累 9.6 个采样点，约 5 秒即可积累 1 ms 左右的误差。因此只在启动时对齐是不够的。

### 2.2 可从已有音频盲估计 SRO

主要方法包括：

- coherence drift / WACD：利用相干函数相位随时间的漂移估计 SRO；
- DXCP（double-cross-correlation processor）：通过二次互相关降低声学传输函数和偏置影响；
- STFT 线性相位漂移拟合；
- 频域相位补偿或异步采样率转换（ASRC）。

Bahari、Bertrand、Moonen 的论文系统研究了基于加权最小二乘相干漂移的盲 SRO 估计。[Blind Sampling Rate Offset Estimation](https://doi.org/10.1109/TASLP.2016.2647713)

Chinaev、Wienand、Enzner 将 DXCP 和 ASRC 组合为在线闭环控制结构。[Control Architecture of the Double-Cross-Correlation Processor](https://arxiv.org/abs/2105.13743)

2023 年的网络级实现可以直接使用网络中已经传输的音频波形，不需要额外校准信号；论文实验中的 DXCP-PHAT SRO 估计 RMSE 约为 0.03 ppm，但该结果依赖特定信噪比、拓扑和声学条件，不能直接视为普通 Windows 设备的保证值。[Springer 论文](https://link.springer.com/article/10.1186/s13636-023-00311-9)

## 3. 数学与音频特征方法

### 3.1 互相关和 GCC-PHAT

普通互相关：

\[
\hat{\tau}=\arg\max_m \sum_n x[n]y[n-m]
\]

GCC-PHAT 使用归一化互谱：

\[
R_{\mathrm{PHAT}}[m]
=IFFT\left(\frac{X(f)Y^*(f)}{|X(f)Y^*(f)|+\epsilon}\right)
\]

最大峰可以作为两路信号的到达时间差。经典论文是 Knapp 和 Carter 的 1976 年工作：[The Generalized Correlation Method for Estimation of Time Delay](https://doi.org/10.1109/TASSP.1976.1162830)。

适用场景：

- 两台设备通过麦克风听到同一个扬声器；
- 两台设备播放相同内容，再由公共麦克风采集；
- WASAPI Loopback 或电子回环信号同步。

GCC-PHAT 测到的是：

\[
\text{设备延迟差}+\text{声学传播差}
\]

因此不能不加区分地把结果全部当作声卡延迟。

### 3.2 包络、能量、过零率、谱平坦度

常用短时能量和包络为：

\[
E_l=\sum_n x_l^2[n]
\]

\[
e_l=LP\left(|x_l+jH\{x_l\}|\right)
\]

然后对两台设备的能量序列或包络序列做相关。包络相关在强混响、远距离麦克风和异步录音下通常比直接波形相关稳定。[Time Delay Estimation Using Signal Envelopes](https://doi.org/10.5281/zenodo.1090884)

Google 的 ICASSP 论文比较了多种音频特征，发现谱平坦度在多录音同步中优于过零率和短时能量；MST 和 Belief Propagation 可以将两两偏移统一求解为全局时间偏移。[Temporal Synchronization of Multiple Audio Signals](https://research.google/pubs/temporal-synchronization-of-multiple-audio-signals/)

### 3.3 音频指纹和 DTW

可使用：

- 频谱峰值对；
- onset；
- Philips Robust Hash；
- 时频 landmark；
- Chroma；
- Log-mel 特征。

Hon 等人提出的 coarse-to-fine landmark 方法在实验中报告了低于 1 ms 的时间偏移误差，但普通音频指纹通常只能达到几毫秒到几十毫秒。[Fine Landmark-Based Synchronization of Ad-Hoc Microphone Arrays](https://www.eecs.qmul.ac.uk/~josh/documents/2015/Hon%20Wang%20-%20EUSIPCO%202015.pdf)

Six 和 Leman 使用环境声音进行音频到音频对齐，可以检测偏移、漂移和丢样本，实验达到毫秒级同步。[Synchronizing Multimodal Recordings Using Audio-to-Audio Alignment](https://doi.org/10.1007/s12193-015-0196-1)

DTW 适合播放速度略有变化、编码版本不同的音频对齐，但对于实时多设备播放，通常应先用指纹或相关获得粗偏移，再用硬件时钟和 ASRC 做连续校正。

### 3.4 全局图优化

如果有多台设备的两两延迟估计，可以求解：

\[
\min_{\beta_i}
\sum_{(i,j)}w_{ij}
\left(\hat{\tau}_{ij}-(\beta_i-\beta_j)\right)^2
\]

固定参考设备 β0=0 后，可通过加权最小二乘或图拉普拉斯方程求解全部节点的相对偏移。MST 计算量较低，Belief Propagation 对异常两两测量更有鲁棒性。

## 4. 物理与基础设施方法

### 4.1 共用音频硬件时钟

这是从根本上消除采样率漂移的方案：

- 同一块多通道声卡；
- 多声卡通过 word clock、ADAT、MADI 或 BNC 锁定；
- 支持统一时钟的 ASIO 多设备驱动；
- Dante、AES67、AVB/TSN 等专业音频网络。

两个 USB 声卡插在同一台 Windows 电脑上，并不代表它们共用采样时钟。

### 4.2 PTP、NTP 与媒体时钟

NTP 或普通软件 PTP 只能让墙上时钟接近，不能自动让两个 DAC 使用同一个采样时钟。专业 AoIP 系统会用 PTP 分发会话时间和媒体时钟。

Carôt 等人的研究指出，Dante、AVB 等方案适合局域网，而 WAN 的毫秒级抖动会影响高精度时钟同步，因此研究了基于 GNSS 的方案。[GNSS-based Sound Card Synchronization](https://annals-csis.org/Volume_18/drp/148.html)

Windows 上更现实的用法是：用 PTP/四时间戳估计会话时间，再将各 endpoint 的实际音频时钟通过 ASRC 拉回共同时间线。

### 4.3 声音到达时间和听音位置

声学传播延迟为：

\[
\tau_i=\frac{d_i}{c}
\]

室温下声速约 343 m/s，1 m 距离约 2.9 ms。实际同步必须明确目标：

- 数字播放同步；
- 扬声器端同步；
- 某个听音位置的声学到达同步。

温度、湿度、风和反射都会影响声学校正。AES 的研究专门分析了温湿度对声速和音响延迟校正的影响。[Environmental Effects on the Speed of Sound](https://secure.aes.org/forum/pubs/journal/?elib=5156)

### 4.4 隐藏同步信号

可以使用嵌入音频的 OFDM、扩频、chirp、MLS 或超声信号。Park 和 Kang 使用嵌入音乐的 OFDM 同步信号估计麦克风位置和时间差。[Position Estimation Using a Microphone and Stereo Loudspeaker](https://dx.doi.org/10.1109/ICASSP.2013.6637692)

这种方式仍属于主动信号，但同步信号可以被设计成听感上不可察觉。

## 5. Windows 非实时系统的实现建议

### 5.1 读取每个 endpoint 的硬件音频时钟

对每个 `IAudioClient` 获取 `IAudioClock`：

```cpp
IAudioClock::GetPosition(&devicePosition, &qpcPosition);
IAudioClock::GetFrequency(&frequency);
```

Windows 文档说明，`GetPosition` 返回的设备位置和 QPC 时间是相关联的，播放秒数可由 \(p/f\) 计算。[IAudioClock::GetPosition](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclock-getposition)

不要只把 `GetFrequency` 当作绝对真实频率。微软文档明确指出，`GetFrequency` 是名义频率，而设备位置会体现实际漂移和抖动，因此应周期性拟合：

\[
p_i(t)=a_i t+b_i
\]

其中 a_i 是实际播放速率，b_i 是当前位置偏移。共享模式下可进一步使用 `IAudioClock2::GetDevicePosition` 获取硬件帧位置。[IAudioClock2::GetDevicePosition](https://learn.microsoft.com/en-us/windows/win32/api/audioclock2/nf-audioclock2-getdeviceposition)

### 5.2 维护应用内会话时钟

不要修改 Windows 系统时间，而是维护映射：

\[
T_{session}=a_iQPC+b_i
\]

网络上使用四时间戳协议估计 offset 和 RTT，并优先使用低 RTT 样本。可以使用鲁棒线性回归或 Kalman 滤波跟踪 offset/skew。

### 5.3 提前启动、延迟呈现

不要等到目标时间才调用 `Start()`。推荐：

1. 每个设备提前打开并启动；
2. 预先写入静音和音频数据；
3. 每个音频帧带统一 `presentationTime`；
4. 到达共同 `START_AT` 时间后才呈现有效音频。

实际听到时间可以拆成：

\[
T_{heard,i}=T_{session}+L_{network,i}+L_{buffer,i}+L_{WASAPI,i}
+L_{DAC/BT,i}+L_{air,i}
\]

同步时应把所有设备延迟到最大路径，而不是强行让慢设备提前。

### 5.4 用 ASRC/PLL 持续修正漂移

设目标缓冲深度为 B*，当前缓冲深度为 B_i：

\[
e_i=B_i-B^*
\]

播放速率可以缓慢调整：

\[
r_i=1+K_pe_i+K_i\int e_i\,dt
\]

缓冲过深时略微加快消耗，缓冲过浅时略微减慢消耗。速率变化应限制在几十到几百 ppm；大幅偏移时使用短时交叉淡化、WSOLA 或相位声码器，避免直接丢样本造成点击声。

### 5.5 WASAPI 配置

- 优先使用 event-driven WASAPI；
- Windows 10+ 使用 `IAudioClient3` 查询最小周期；
- 支持时使用 WASAPI Exclusive；
- 低延迟线程注册 MMCSS 的 `Audio` 或 `Pro Audio` 任务；
- 不用普通 `Sleep()` 作为音频时钟；
- 记录 underrun、padding、QPC 和 `IAudioClock` 位置；
- 注意共享模式的 Audio Engine、APO 和系统重采样；
- `IAudioClient3` 可查询设备支持的周期范围。[GetSharedModeEnginePeriod](https://learn.microsoft.com/en-us/windows/win32/api/audioclient3/nf-audioclient3-getsharedmodeengineperiod)

WASAPI 独占模式和 ASIO 能降低延迟，但不能自动消除两个独立声卡之间的采样率偏差。[Windows Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)

MMCSS 只提供软实时优先级，不是硬实时保证。[Multimedia Class Scheduler Service](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)

## 6. 对 VoiceSpreader 的推荐组合

### 局域网、多台 Windows/Android

1. 一个源设备只编码一次音频；
2. 音频帧携带 `streamId + sequence + presentationTime`；
3. 使用四时间戳估计会话时钟；
4. 每个 Windows endpoint 周期性读取 `IAudioClock`；
5. 每个设备根据本地硬件时钟进行 ASRC；
6. 通过缓冲深度闭环控制速率；
7. 启动或路由变化时做一次固定延迟校准；
8. 需要听感同步时，再用麦克风做 GCC-PHAT 或包络相关校正。

### 不使用主动探针

可采用：

- 网络时间戳：解决数字播放时间；
- `IAudioClock`：解决设备采样时钟；
- GCC-PHAT、包络、音频指纹：利用自然音频估计相对延迟；
- coherence drift/DXCP：长期跟踪采样率偏差；
- ASRC：持续修正。

但如果实际 DAC、Bluetooth 或扬声器延迟没有任何观测路径，就不能保证绝对声学同步。可以把主动探针降级为一次性校准工具，而不是持续同步机制。

## 7. 建议的测试指标

- 数字播放偏移的 p50/p95/p99；
- 声学到达偏移的 p50/p95/p99；
- 长时间运行的最大漂移 ppm；
- underrun/overflow 次数；
- ASRC 速率变化范围；
- CPU 负载、DPC 延迟和线程唤醒抖动；
- 普通音频、语音、低信噪比、混响、Bluetooth 路由切换下的表现。
